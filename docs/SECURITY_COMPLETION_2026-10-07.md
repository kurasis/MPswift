# Security completion: mutable files and restore transactions

Baseline `f8716db56be15821563cb3eb03a2d4352fa60d23`, build `0.2.77-dev.1`, [successful run 37614245760](https://github.com/kurasis/MPswift/actions/runs/37614245760): 270 tests on each OS, 216 isolated parser cases, restricted file controls, EN/RU/extracted WPF and independent 577-file/13-native ZIP verification passed. Inspection preceded owned-data execution. The owner explicitly approved rejecting symbolic/hard links in mutable application data; music and local directory links retain their existing support.

## SEC-18 — Mutable data file links

- Priority/risk: P2, conditional local data integrity. A writer with access to an app data directory can substitute its main database, WAL/SHM or settings with a link. Prior main SQLite path opening could then modify an unrelated database. A source-equivalent positive control uses the pinned SQLite dependency and owned databases to demonstrate writes through a symbolic link. This is not remote execution, elevation or an OS boundary against malware running as the same user.
- Files: `SqlitePlayerStore.Open/Run`, `SettingsFile.Load/LoadBackup/Save/RestoreBackup`, `DataFileLease`, `RestoreFileTransaction.HeldFile.OpenOriginal`.
- Correction: open Windows file entries without following reparse points, inspect availability/type/link count through the same handle, reject nonregular/recalled/symbolic/hardlinked mutable entries, and retain no-delete name pins. SQLite main/WAL/SHM entries are checked/reserved before native opening and held until native close. Validated settings are read through held writer-denying handles; settings replacement uses held objects. Fresh companion placeholders can remain after a rejected open; original bytes are preserved. Native last-close cleanup can leave checkpointed WAL/SHM while pins exist; these are checked again on the next open.
- Compatibility: local directory aliases remain supported; public methods, schemas, codec support and valid size limits are unchanged. A process-wide settings I/O gate keeps distinct settings instances from observing the temporary absence introduced by the multi-file transaction. A successful save keeps the immediately previous main file in `.bak`; the older backup is removed by its held handle only after commit. An explicit recovery retains the original in its existing preserved-name convention.
- Limits: writable SQLite sharing permits native SQLite updates to the held objects. This does not forbid arbitrary same-user direct writes or memory-mapped edits. Linux tests reject symbolic links but do not establish Windows hardlink/sharing guarantees or form a portable filesystem sandbox.

## Restore validation, publication and rollback (race hardening)

- Priority: P2. Existing parent pins did not establish child identity from extraction to parsing/installation; rollback deleted installed filenames and reopened original preserved names. Deterministic exploitation of each prior interval is not claimed.
- Files: `BackupBundle.ExtractValidated/RestoreAsync/Install/CreateAsync`, `DatabaseRecovery.Restore`, `RestoreFileTransaction`, `SqlitePlayerStore.ReadOnlyValidation/CheckpointAsync`.
- Correction: retain extracted name pins before closing output handles, verify actual frozen bytes against the manifest, keep settings frozen, and revalidate the final checkpointed database with the actual production loader through read-only `immutable=1` SQLite. Current-schema bundles remain writer-denied throughout. Legacy schema-one migration temporarily allows SQLite writes under a continuous name pin and is followed by frozen production validation. The immutable route is used only for an owned, checkpointed, writer-denied snapshot; ordinary live databases still use WAL.
- Installation: copy the frozen input into fresh exclusively held prepared files, open all originals before moving anything, then rename the same Windows objects with `SetFileInformationByHandle`. Held files cannot be replaced/written through ordinary competing handles. Rollback deletes installed owned objects by handle and restores retained objects by handle; an occupied rollback name is not overwritten and all failures/originals are retained. Originals keep the previous `.preserved-*` naming convention. An archive is written, flushed and published using the same owned handle. Raw SQLite recovery freezes/revalidates its copied database before installing a separately owned copy; temporary cleanup compares captured volume/file identity/creation information on the newly opened no-follow delete handle and refuses a replacement object.
- Tradeoff: preparation needs an additional database-sized temporary copy; disk-full refusal preserves originals. Cross-file installation is not a filesystem-wide atomic commit or a physical power-loss transaction. If rollback is blocked, retained originals require explicit recovery. Unknown staging contents remain protected by nonrecursive cleanup.
- Residuals: same-user in-place writes during authorized legacy migration, malicious memory mapping/process tampering and an exact generated-name stage contamination are not ruled out. Selected read-only backup file links remain compatible; source SQLite snapshotting is validated again after copying. No checksum is claimed to authenticate a publisher. Prepared-file Windows guarantees do not apply to the path-based Linux fallback.

### Windows rename regression found before publication

Run [37622947015](https://github.com/kurasis/MPswift/actions/runs/37622947015) passed all 283 Linux tests but failed 20 Windows tests; no build was released. The Windows destination buffer lacked a terminating UTF-16 NUL during Win32 DOS-path conversion, leading to rejected or unintended names. The buffer now includes and initializes the terminator while excluding it from FileNameLength. A repeated 64-name Unicode publication regression verifies exact destinations and no leftover partials. Windows commit/rollback/backup behavior must pass unchanged assertions in the next run.
