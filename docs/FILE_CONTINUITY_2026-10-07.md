## SEC-16 — Waveform cache touch follows a different file object (low conditional integrity)

- File/section: `Services/Storage/WaveformCache.cs`, ReadCore file opening and LRU timestamp update.
- Confirmed mechanism: a cache entry was opened through an arbitrary file link, and a successful read subsequently called `File.SetLastWriteTimeUtc(path, ...)`, reopening by name. A valid cache linked to an unrelated same-format file was accepted in the baseline regression instead of being treated as disposable/invalid. Both .NET 10.0.12 Windows and the observed Linux path setters update the symbolic-link object itself; the initial symbolic-link regression demonstrates acceptance of externally linked cache data, not a changed target timestamp. Hardlinks name one shared file object, and their timestamp change was independently reproduced using the actual .NET API on owned Linux files. Thus a symbolic link alone is not claimed to change its target timestamp on either tested OS. Reopening also introduces a name/object gap; the existing directory lease does not establish individual file identity.
- Conditions/damage: a process with write permission in the application's cache places a symbolic/hard link or substitutes an individual entry. The target must contain a valid matching waveform cache for the successful-read path. Its timestamp can change, affecting backup/index decisions. No target byte overwrite, remote access, arbitrary command execution or privilege escalation is established. Same-user writable storage is not a malware isolation boundary.
- Minimal correction: Windows opens the leaf reparse object with read plus write-attributes permission and share-read only; handle attributes reject directory/offline/recall/reparse objects and link counts other than one. The existing directory lease pins the physical chain. LRU timestamp update uses the same handle that read/validated the cache. Invalid linked entries become cache misses, and normal atomic regeneration replaces only the cache entry. Music paths and local directory-link support are not changed. Linux storage tests check links before opening and use handle-based timestamps; this is not a portable path-race sandbox.
- Targeted verification: the baseline linked-cache regression failed; the corrected synthetic symbolic-link case verifies target bytes/timestamp and regeneration. A normal-file test verifies unchanged bytes and actual LRU eviction after access. Disposable Windows restricted-token controls additionally require rejection of symbolic and hardlinked cache entries, platform-correct link-object/shared-hardlink timestamp positive controls, unchanged outside targets, replacement-only regeneration, successful handle LRU touch, released handles and safe clearing of a still-linked entry. These new Windows controls require this source's CI; they are not claimed from Linux.

## Atomic new SQLite destinations (hardening of a source-observed race)

- Files/sections: `SqlitePlayerStore.BackupAsync`, `SqliteLibraryIndex.AddIndexSchema` migration backup, and `DatabaseRecovery.Restore` temporary destination.
- Source finding: checking absence, then asking SQLite ReadWriteCreate to open by path does not atomically reserve a new file. A competing writer with directory access can introduce a file in that interval; SQLite backup can replace contents of an existing database. Existing-file rejection is part of the application contract. No deterministic exploitation of this interval on Windows is asserted here; this is justified race hardening, separate from the reproduced cache defect.
- Correction: `FileMode.CreateNew` reserves the destination, retaining a read/write-sharing handle without delete sharing while SQLite opens the same existing empty file in ReadWrite mode and copies the database. The handle prevents Windows name replacement during the copy and rejects occupied names atomically. Backup connection closes before the reservation. Recovery releases the reservation before its existing install/rollback workflow. Public APIs, schemas, backup contents and source database policy remain intact.
- Verification: existing live-WAL/complete-backup/recovery/migration/maximum-state tests pass. New occupied-file, existing-link and dangling-link cases preserve the target and keep the source store usable. The dangling-link check already passed on the baseline; it is compatibility coverage, not a falsely attributed reproduced vulnerability.

## First Windows observation and corrected test premise

[Run 37609245602](https://github.com/kurasis/MPswift/actions/runs/37609245602) at `837185b62cf09c3bdb695457795f770f0b6ccaec` passed 263 tests on each OS and native/EN/RU WPF, but the new isolated control incorrectly expected a symbolic path setter to change its target on Windows. The suite stopped on that assertion; no ZIP was published. The official [.NET 10.0.12 FileSystem.Windows.cs](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Windows.cs#L220) explicitly opens FILE_FLAG_OPEN_REPARSE_POINT when setting attributes by path. The corrected control requires changed symbolic-link object metadata and unchanged target, while a separate hardlink control must change the shared file object's timestamp. Both now inspect times by handles, avoiding per-name NTFS metadata caching. Rejection, regeneration, target preservation, LRU and handle-release assertions remain required. Corrected source needs its own Windows execution; this is not a rerun intended to hide a failed check.


The owned Linux .NET 10.0.12 timestamp control also confirmed unchanged symbolic target metadata and changed shared hardlink metadata, with unchanged bytes. The official [pal_time.c](https://github.com/dotnet/runtime/blob/v10.0.12/src/native/libs/System.Native/pal_time.c) uses AT_SYMLINK_NOFOLLOW for path setters. The original regression only observed linked cache acceptance before failing its first assertion; no target timestamp change is inferred from that failure. [Exact owned control](evidence/file-time-control-linux.json). Windows hardlink/rejection/regeneration results still require the corrected source run.
