## SEC-16 — Waveform cache touch follows a different file object (low conditional integrity)

- File/section: `Services/Storage/WaveformCache.cs`, ReadCore file opening and LRU timestamp update.
- Confirmed mechanism: a cache entry was opened through an arbitrary file link, and a successful read subsequently called `File.SetLastWriteTimeUtc(path, ...)`, reopening by name. A valid cache linked to an unrelated same-format file was accepted in the baseline regression instead of being treated as disposable/invalid. The path-based timestamp operation can modify the linked target. Reopening also introduces a name/object gap; the existing directory lease does not establish individual file identity.
- Conditions/damage: a process with write permission in the application's cache places a symbolic/hard link or substitutes an individual entry. The target must contain a valid matching waveform cache for the successful-read path. Its timestamp can change, affecting backup/index decisions. No target byte overwrite, remote access, arbitrary command execution or privilege escalation is established. Same-user writable storage is not a malware isolation boundary.
- Minimal correction: Windows opens the leaf reparse object with read plus write-attributes permission and share-read only; handle attributes reject directory/offline/recall/reparse objects and link counts other than one. The existing directory lease pins the physical chain. LRU timestamp update uses the same handle that read/validated the cache. Invalid linked entries become cache misses, and normal atomic regeneration replaces only the cache entry. Music paths and local directory-link support are not changed. Linux storage tests check links before opening and use handle-based timestamps; this is not a portable path-race sandbox.
- Targeted verification: the baseline linked-cache regression failed; the corrected synthetic symbolic-link case verifies target bytes/timestamp and regeneration. A normal-file test verifies unchanged bytes and actual LRU eviction after access. Disposable Windows restricted-token controls additionally require rejection of symbolic and hardlinked cache entries, old path-touch positive controls, unchanged outside targets, replacement-only regeneration, successful handle LRU touch, released handles and safe clearing of a still-linked entry. These new Windows controls require this source's CI; they are not claimed from Linux.

## Atomic new SQLite destinations (hardening of a source-observed race)

- Files/sections: `SqlitePlayerStore.BackupAsync`, `SqliteLibraryIndex.AddIndexSchema` migration backup, and `DatabaseRecovery.Restore` temporary destination.
- Source finding: checking absence, then asking SQLite ReadWriteCreate to open by path does not atomically reserve a new file. A competing writer with directory access can introduce a file in that interval; SQLite backup can replace contents of an existing database. Existing-file rejection is part of the application contract. No deterministic exploitation of this interval on Windows is asserted here; this is justified race hardening, separate from the reproduced cache defect.
- Correction: `FileMode.CreateNew` reserves the destination, retaining a read/write-sharing handle without delete sharing while SQLite opens the same existing empty file in ReadWrite mode and copies the database. The handle prevents Windows name replacement during the copy and rejects occupied names atomically. Backup connection closes before the reservation. Recovery releases the reservation before its existing install/rollback workflow. Public APIs, schemas, backup contents and source database policy remain intact.
- Verification: existing live-WAL/complete-backup/recovery/migration/maximum-state tests pass. New occupied-file, existing-link and dangling-link cases preserve the target and keep the source store usable. The dangling-link check already passed on the baseline; it is compatibility coverage, not a falsely attributed reproduced vulnerability.

## Temporary cleanup ownership (defensive correction)

Settings Save/RestoreBackup, waveform writes, complete backup creation and database restore now record successful creation before deleting a temporary path. A failed CreateNew collision must not authorize deleting the pre-existing entry. Restore settings serialize under the already held directory lease so a partial owned write is still cleaned. This does not claim handle-relative cleanup: substitution after handle release and the existing release-before-stage-recursive-cleanup interval remain open.
