## Findings

### UI-01 — P1 — Playlist deletion has no confirmation or undo

- Location: `src/Player.App/Views/MainWindow.xaml.cs:384`; `src/Player.App/ViewModels/PlayerViewModel.cs:616`.
- Trigger: choose Delete playlist from the tab or action menu. The callback immediately removes the tab and its entries; there is no confirmation or undo path. Music files are not deleted, but the user-created playlist and ordering are lost.
- Minimal fix: a confirmation naming the playlist and entry count, with Cancel as the default, or a reliable undo action preserving entry identities and order.
- Verification: cancel leaves the playlist unchanged; confirm affects only the intended playlist; undo, if chosen, restores the exact entries and order across persistence.

### UI-02 — P2 — Audio controls lack associated accessible labels

- Location: `src/Player.App/Views/AudioSettingsWindow.cs:23`, `:27`, `:33`, `:36`, `:38`.
- Visual labels are separate TextBlocks without `AutomationProperties.LabeledBy` or explicit control names. Equalizer sliders share the same generic gain tooltip, so their frequencies are not conveyed as distinct control names.
- Minimal fix: associate captions with each control and give every band a localized accessible name including frequency and units; name preamp, crossfade, device and ReplayGain controls.
- Verification: UI Automation peers expose distinct localized names and numeric ranges; Narrator identifies each frequency and setting.

### UI-03 — P2 — Audio Apply accepts repeated requests while busy

- Location: `src/Player.App/Views/AudioSettingsWindow.cs:57`.
- Apply remains enabled throughout `ConfigureAudioAsync`, with no progress indication or request guard. Repeated clicks can enqueue repeated configuration operations. This is a UI defect; a native concurrency exploit is not established.
- Minimal fix: disable Apply after the request starts, show a localized busy state and re-enable it on failure.
- Verification: rapid activation invokes configuration once; success closes the dialog; failure restores the button and retains settings for correction.

### UI-04 — P2 — Audio configuration errors appear behind the modal dialog

- Location: `src/Player.App/Views/AudioSettingsWindow.cs:57`.
- The catch handler writes only to the main view model's status/details. The modal audio window remains open without an inline failure message, while the status is behind it.
- Minimal fix: show the error and a useful retry/device-selection step in the audio dialog, with an accessible status announcement. Retain technical details in the existing diagnostics surface.
- Verification: an unavailable output or controlled configuration failure produces a visible, announced message without closing the dialog or losing the selected settings.

### UI-05 — P2 — Library pagination allows navigation past the last page

- Location: `src/Player.App/Views/LibraryWindow.cs:33`, `:61`; backing query `src/Player.App/Services/Storage/SqliteLibraryIndex.cs:50`.
- Next increments the offset unconditionally. The query retains that offset even if no rows remain, and the status calculates the first position as offset + 1. With one result, Next yields an empty page and a range of 101–100.
- Minimal fix: disable Previous/Next at their boundaries, reconcile the offset when the result count changes, and display a valid empty range. Keep stale-response protection.
- Verification: cover 0, 1, 100 and 101 results, boundary navigation, filtering and result-count changes on a later page.

### UI-06 — P2 — Search, root selection and playlist-name fields lack accessible labels

- Location: `src/Player.App/Views/LibraryWindow.cs:34`, `:37`; `src/Player.App/Views/PlaylistNameDialog.cs:17`.
- Search has only a tooltip; root selection and the name field have no associated caption/name. A window title does not associate a label with its input.
- Minimal fix: provide visible captions and `AutomationProperties.LabeledBy` or localized names, preserving search debounce and initial name selection.
- Verification: EN/RU automation peers identify search, root selection and playlist-name entry independently.

### UI-07 — P2 — Saving an empty playlist name silently does nothing

- Location: `src/Player.App/Views/PlaylistNameDialog.cs:20`.
- Empty or whitespace-only input leaves the enabled Save button without any error feedback.
- Minimal fix: show a localized inline validation error, associate it with the field and focus the field on invalid submission.
- Verification: empty/whitespace submissions show the error and preserve the dialog; valid trimmed input saves normally.

### UI-08 — P2 — Auxiliary async/validation statuses lack explicit live announcements

- Location: `src/Player.App/Views/LibraryWindow.cs:36`, `:61`; `src/Player.App/Views/PreferencesWindow.cs:44`, `:142`, `:153`; `src/Player.App/Views/FileInformationWindow.cs:70`, `:101`.
- These status TextBlocks change text without the explicit polite live-region configuration and event used by the main window. Settings validation focuses the invalid field, but does not associate the error message with it.
- Minimal fix: use the existing WPF live-region pattern for significant completion/error updates and associate validation text with the cache-budget field. Avoid announcing every keystroke or routine playback update.
- Verification: automation events accompany completion/errors and field validation; Narrator announces the relevant message once without excessive chatter.

### UI-09 — P3 — Accent buttons have no distinct hover appearance

- Location: `src/Player.App/Themes/Dark.xaml:75`, `:82`.
- The shared hover trigger sets the border to AccentBrush, which AccentButton already uses. Hover therefore produces no visible change for those buttons. Pressed and keyboard-focus feedback already exist.
- Minimal fix: add a distinct accessible hover border/background for AccentButton while retaining pressed, disabled and focus states.
- Verification: compare resting/hover/pressed/focused/disabled states in each supported accent theme.

### UI-10 — P2 — Desktop-panel positioning has only a drag gesture

- Location: `src/Player.App/Views/DesktopPanelWindow.cs:113`.
- The panel can be repositioned by pointer dragging only. Its deliberate nonactivating behavior also prevents using focused panel controls as a keyboard movement surface. Main-window transport shortcuts remain available; this finding concerns positioning only.
- Minimal fix: expose accessible position presets or Move/Reset controls in the main-window settings, preserving the requested nonactivating panel behavior.
- Verification: keyboard-only users can change/reset position through the main window; dragging, saved coordinates and behind-window placement remain intact.
