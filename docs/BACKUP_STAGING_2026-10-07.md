# Backup staging and checksum follow-up

Baseline: `51e85d3213b210f2715ce148712f541aedef078f`, development build `0.2.76-dev.1`, [successful main run 37610865422](https://github.com/kurasis/MPswift/actions/runs/37610865422). Its 263 tests on each OS, 216 bounded parser cases, restricted Windows file controls, EN/RU/extracted WPF and 577-file/13-native package audit passed. The independently downloaded ZIP and compiled versions were verified. Static inspection preceded owned-data tests in this follow-up.

## SEC-17 — Recursive removal of uncertain staging contents

- Priority/risk: P2, low conditional data integrity/availability. A process or producer must place unrelated data inside the random backup/restore stage, requiring access to that directory. Recursive deletion can then remove those contents. The release-before-recursive-delete interval also permits directory name replacement in principle; deterministic exploitation of that race is not claimed. No remote attack, privilege escalation or ZIP path traversal is established.
- Files/sections: `Services/Storage/BackupBundle.cs`, both finally blocks after creation/restore; the old code disposed the directory lease and then called `Directory.Delete(stage, true)`.
- Confirmed behavior: two owned-data integration regressions supply a failing store that creates an unrelated flat file or nested folder inside the stage. Both failed on the baseline because cleanup deleted the sentinel. This demonstrates destructive cleanup of unexpected contents, not a reproduced Windows race.
- Minimal correction: `BackupStageCleanup.Clean` removes only the flat metadata filenames produced by backup/SQLite/settings, plus strictly shaped schema-migration snapshots. It keeps the Windows directory chain pinned during those deletions. After releasing the pin, it requests only an empty, nonrecursive root deletion. Unexpected files/directories are retained and reported; a nonempty replacement root cannot be recursively traversed. If the operation and cleanup both fail, all collected causes are retained, including partial-archive cleanup failures.
- Compatibility: successful and rejected bundles still clean normal stages; legacy schema-one bundles still migrate, restore and remove their generated migration snapshot. Known metadata filenames occupied by directories are not traversed. File-link deletion removes the link entry and preserves its target. Locks are released after successful and failed cleanup.
- Remaining boundary: deletions of known filenames and the final empty root are still path-based. This is not a complete handle-relative identity transaction. A same-user attacker can still substitute individual entries at unprotected transitions; accidental data using an exact generated filename is not distinguished by filename alone. An unexpected stage can retain sensitive database copies and requires manual review; no recursive retry should be used.

## Backup hash/archive continuity (defensive correction)

- Files/sections: `BackupBundle.CreateAsync` source hashing/ZIP copying and `ExtractValidated` decompression/checksum.
- Source finding: creation hashed by one path open and subsequently archived through another; restore closed an extracted output before reopening its pathname to hash it. Parent directory pins do not establish child-file identity. No deterministic exploitation of these intervals is asserted.
- Minimal correction: creation retains both read handles from size validation through hashing and ZIP copying. Windows read sharing permits readers but refuses writers/name replacement while those handles are held. Size caps now run before hashing. Restore hashes each written chunk while the exclusive output handle remains open, retaining declared-size and checksum checks without reopening the path. Memory remains bounded by the existing 64 KiB copy buffer.
- Compatibility: public methods, ZIP member names/manifest schema, size limits, SHA-256 spelling, source audio, dependencies and saved schemas are unchanged. Existing live-WAL, malicious/checksum/truncated/duplicate/traversal archives, occupied settings and active-store refusal tests remain applicable.
- Remaining boundary: extracted files are subsequently reopened by settings/SQLite and later moved by Install. Validation-to-install and rollback-name races, mutable main DB/settings hardlinks, WAL companions and native streaming/WVC continuity remain open. The checksum is integrity relative to the manifest, not archive publisher authentication. Linux storage tests do not establish Windows sharing semantics or provide a portable filesystem sandbox.

## Verification

The baseline locked Release build passed **263** tests with zero warnings/errors. The two new baseline regressions failed at sentinel preservation. The corrected locked build passes **270** managed tests, zero failures/skips/warnings/errors. Existing SDK/xUnit analyzers execute during compilation; separate lint/type commands are not configured. Seven added cases cover unexpected flat/nested contents and original causes, normal generated/migration cleanup, directory collisions, unlink preservation, unknown migration lookalikes and actual schema-one bundle migration. [Source and managed counters](evidence/backup-staging-managed-2026-10-07.json).

The existing disposable Windows workflow additionally runs synchronous production cleanup under the restricted impersonation token: pinned-stage movement must fail, normal flat cleanup must succeed, unexpected nested contents must survive, and directory movement after both cleanup paths must succeed. This source's Windows/native/WPF/package checks and publication require their own successful main run before handoff; prior baseline results do not pre-approve changed source.

Not changed or claimed: parser process isolation, native codec implementation/provenance, installation/update behavior, publisher signing, clean Windows 11, physical output/latency/hotplug/sleep, Narrator/DPI, two-hour full-player output and owner licensing decisions. [Consolidated remaining work](REMAINING_WORK.md). This follow-up does not establish complete application safety.
